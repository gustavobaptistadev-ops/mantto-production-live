# ADR-0005: Uso de SQLite no ambiente de desenvolvimento local (MVP) e Postgres em Produção

## Contexto
O projeto foi inicialmente desenhado para usar PostgreSQL. Porém, conforme o ADR-0003, decidimos rodar os serviços de forma nativa no Windows sem Docker. Ao executar os binários portáteis do PostgreSQL, encontramos erros de DLLs do Visual C++ Redistributable ausentes no ambiente. Isso cria uma fricção alta e bloqueia o desenvolvimento local (bottleneck).

## Problema
Como destravar o desenvolvimento do MVP e permitir execução de testes isolados e TDD sem depender de uma instalação complexa de banco de dados nativa na máquina do desenvolvedor, mantendo a compatibilidade futura com PostgreSQL para Produção?

## Alternativas
1. Obrigar a instalação global do VC++ Redistributable (requer privilégios de administrador).
2. Voltar a usar Docker para o banco de dados (viola ADR-0003).
3. Utilizar SQLite no desenvolvimento local (`sqlite+aiosqlite`) e testes, mantendo o SQLAlchemy ORM limpo e utilizando PostgreSQL apenas no ambiente de Homologação/Produção.

## Decisão
Adotar a **Alternativa 3**. 
- O ambiente `development` e os testes unitários (`pytest`) usarão SQLite (`sqlite+aiosqlite`).
- O Alembic será configurado para gerar migrations compatíveis com PostgreSQL, porém suportaremos a criação do schema no SQLite local via `Base.metadata.create_all()` durante os testes.
- Evitaremos tipos exclusivos do Postgres (ex: JSONB profundo que falhe no SQLite) usando o tipo `JSON` genérico do SQLAlchemy que adapta para JSON/Text no SQLite e JSONB no Postgres.

## Consequências
- Destravamos imediatamente o desenvolvimento (TASK-0006, TASK-0007).
- Ambiente local torna-se "zero setup" (basta o `pip install` e rodar a API).
- Atenção extra ao escrever queries nativas (deve-se usar a sintaxe SQLAlchemy).

## Status
ACCEPTED
