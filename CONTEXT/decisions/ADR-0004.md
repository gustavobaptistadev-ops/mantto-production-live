# ADR-0004 — Arquitetura SOLID enxuta e pragmática

## Status
ACCEPTED (instrução explícita do dono do projeto em 2026-10-08)

## Contexto
O briefing cita Clean Architecture, DDD, SOLID, filas, circuit breaker etc. Risco: over-engineering e excesso de camadas, ruim para múltiplas IAs mantendo o código.

## Problema
Definir o nível de arquitetura: o suficiente para segurança, testabilidade e troca de fornecedores, sem cerimônia.

## Alternativas
1. Clean Architecture/DDD completos (entities/use cases/repositories/DTOs em todo módulo) — rejeitado por custo.
2. Código simples sem fronteiras — rejeitado (risco de acoplamento ao WhatsApp/pagamento/LLM).
3. SOLID enxuto e pragmático — escolhido.

## Decisão
- **Módulos por domínio** em `mantto_api/modules/<nome>/` (ex.: catalog, inventory, orders, payments), cada um com `models`, `schemas`, `service`, `router` (e `providers` quando houver integração).
- **Service layer** concentra regras de negócio; routers finos; sem repositório genérico — usar SQLAlchemy direto no service, salvo se houver ganho real.
- **Interfaces (Protocol) somente nas fronteiras externas** que precisam ser trocáveis: `PaymentProvider`, `ShippingProvider`, `WhatsAppProvider`, `LLMClient`. Injeção de dependência via FastAPI `Depends`/construtor.
- **Sem abstração especulativa:** só criar interface/camada quando houver 2ª implementação real ou necessidade de teste/isolamento comprovada. Regra de 3 antes de generalizar.
- Funções pequenas e puras para regras (máquina de estados de pedido, cálculo de totais); testáveis sem I/O.
- Módulos não importam internals uns dos outros: comunicação pela interface pública (`service`) do módulo.
- Fila/retry/circuit breaker: apenas onde há integração externa instável (webhooks, WhatsApp, pagamento); sem framework de eventos interno.
- Dependências novas exigem justificativa; preferir stdlib/FastAPI/SQLAlchemy.
- Revisão (Reviewer Agent) rejeita camadas, classes ou padrões sem uso atual.

## Consequências
+ Menos código, mais fácil de entender por qualquer IA, troca de fornecedores preservada.
- Exige disciplina para não vazar lógica de negócio para routers; refatorar quando a complexidade justificar.
